# 24 · 浏览器为什么拦截请求

## 目标与原理

理解同源、CORS、预检与相关响应头。先修按 [完整目录](../CURRICULUM.md) 的章节关系；基础操作、原理关系随本课讲解。

CORS 是浏览器对跨源响应访问的限制；跨源不等于跨站，预检也不是业务请求。

### 先建立边界

协议、主机、端口决定 origin；两个本机端口也跨源

### 再核对证据

自定义请求头会触发 OPTIONS，预检失败时业务 POST 不会发送

### 最后验证结果

实际响应也需要允许来源；不要用 no-cors 伪装修复，opaque 响应无法读取业务内容

## 真实商城合同

症状：跨到另一个本机端口后，fetch 出现 TypeError。

正常结果：OPTIONS 满足需要，POST 实际响应允许来源，浏览器可读取 JSON。

真实机制：实际 4174→4175 跨源。配置一预检拒绝，配置二实际响应缺少 CORS 头。

1. 从本课准备并打开独立商城；先打开 DevTools，再运行故障。
2. Network 同时看 OPTIONS 和 remote 请求，不只看 Console 的一句报错。
3. 比较 Access-Control-Request-Headers 与 Allow-Headers，以及实际响应 Allow-Origin。
4. 本机 4175 是独立跨源服务；对照后恢复可读取 JSON，记录预检与实际请求分别发生了什么。
5. 先保存证据，再应用针对性的对照；错误对照不会通过页面检查。

## 独立挑战与参考答案

区分未发送、预检失败和响应不可读取。新会话改变输入与故障配置，可能再次抽到同一类型；按实际证据判断。

| 配置 | 原因 | 证据 | 修复/验证 |
| --- | --- | --- | --- |
| 配置1 | OPTIONS 没有允许需要的自定义请求头 | 预检拒绝且没有随后的业务 POST | 允许具体来源、方法和需要的请求头 |
| 配置2 | POST 已返回但实际响应缺少允许来源 | 预检通过、POST 存在，响应却不可读取 | 在实际响应返回匹配来源的 CORS 头 |
| 干扰项 | 只凭界面颜色判断 | 没有对应请求或存储证据 | 同时改变全部条件且不复测 |

## 边界与恢复

端口跨源不等同跨站。no-cors 产生 opaque 响应，不当作业务修复。

清理与会话约定见 [共同合同](../NETWORK-APPLICATION.md)。请在复盘写下条件、观察对象、实际值、根因、最小修改与恢复设置；将 HTTP 缓存、Cache Storage、内存状态分开。
