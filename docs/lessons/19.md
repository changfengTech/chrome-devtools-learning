## 真实商城合同

症状：搜索结果不正确，记录里还混着埋点与重复调用。

正常结果：一次搜索仅产生一个含 q=cup 的 search 请求，返回一件目标商品。

真实机制：实际 analytics 噪声与 search 请求。配置一遗漏参数，配置二重复调用。

1. 从本课准备并打开独立商城；先打开 DevTools，再运行故障。
2. 清空 Network，确认录制中，再运行故障；只进行一次搜索。
3. 筛选 search，再比较 Payload、Response 和 Initiator；不要将 analytics 当成搜索。
4. 勾选 Preserve log 后刷新比较记录；导出 HAR 前核对可能包含的 Cookie、参数与响应。
5. 先保存证据，再应用针对性的对照；错误对照不会通过页面检查。
6. 回到教程选择真实证据，完成独立挑战后写下排查与恢复步骤。

## 独立挑战与参考答案

在混杂记录中找出一次筛选请求。新会话改变输入与故障配置，可能再次抽到同一类型；按实际证据判断。

| 配置 | 原因 | 证据 | 修复/验证 |
| --- | --- | --- | --- |
| 配置1 | 搜索参数未随输入发送 | Query String 中缺少 q，返回全部商品 | 传入当前搜索条件并重发 |
| 配置2 | 同一操作重复发送搜索请求 | 一次动作出现两条相同搜索与调用来源 | 消除重复调用并用一次动作复测 |
| 干扰项 | 只凭界面颜色判断 | 没有对应请求或存储证据 | 同时改变全部条件且不复测 |

## 分级提示

1. 先区分实际请求、浏览器策略、存储与界面处理，记录第一次偏离的环节。
2. 清空 Network，确认录制中，再运行故障；只进行一次搜索。
3. 比较两个候选解释：搜索参数未随输入发送；同一操作重复发送搜索请求。保持其他输入一致再验证。

## 边界与恢复

关闭录制/过滤只改变可见记录；HAR 可能含敏感数据，分享前检查。

清理与会话约定见 [共同合同](../NETWORK-APPLICATION.md)。请在复盘写下条件、观察对象、实际值、根因、最小修改与恢复设置；将 HTTP 缓存、Cache Storage、内存状态分开。

[官方参考](https://developer.chrome.com/docs/devtools/network/reference)。实测范围见 [验收记录](../QA-NETWORK-APPLICATION.md)。
