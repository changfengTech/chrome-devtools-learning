# 40 · 内存增长一定是泄漏吗

由 pnpm docs:lessons 生成。内容源 src/data/memory.json；生成与合同 scripts/generate-memory.mjs。本页含教师参考答案。

## 学习目标与原理

理解可达性、GC 和正常波动，使用 Performance monitor。对象不可达后才可能回收；分配高峰、缓存平台和持续保留是不同现象。先建立重复操作、静置、GC 后的同条件趋势。

### 可达性决定回收资格

关闭弹窗只是业务生命周期结束。全局数组、缓存、监听器等仍可能使对象可达；不可达也不保证立即回收。

### 观察多个信号

Performance monitor 的 JS heap、DOM Nodes、JS event listeners 是浏览器信号。页面只统计自己拥有的资源，不将这些计数冒充整个堆。

### 平台与增长

正常缓存可有有界平台。按相同 5 次开关分组，先预热，再比较 GC 后多个点；一次上升或一次下降都不能证明泄漏。

## 交互演示

对比暂时分配、稳定缓存与持续保留。改变临时分配、缓存或持续保留模式；重复相同批次，再模拟一次 GC；比较回收后的基线和平台；这是示意单位，不是浏览器字节。模型不计完成。

## 商城实战

商品预览反复开关后，页面仍能用，但已关闭预览对应的业务记录不断增加。

1. 打开 More tools > Performance monitor，固定页面与每组 5 次开关，先记录空闲基线。
2. 准备故障，在同一文档重复 5 次开关至少两组，记录 JS heap、DOM 和监听器趋势。
3. 在 Memory 使用 Collect garbage 后再次记录；不要把临时峰值直接称为泄漏。
4. 在 Heap snapshot 用 MemoryVisit / CatalogEntry 筛选，沿 history / cache 查看可达路径。
5. 选择对应清理或有界缓存对照，在同一文档再做相同批次；功能结果应保持。
6. 记录正常平台、仍保留的根、观察条件和不能由计数推出的结论，再记录本轮检查。

## 独立挑战与答案

设计重复操作与正常对照。输入与故障随机变化，可能再次抽到同类。

| 配置 | 根因 | 证据 | 针对性验证 |
| --- | --- | --- | --- |
| 配置1 | 关闭预览后历史数组持续保留 MemoryVisit | 相同批次后 history 中存活对象持续增长 | 关闭后移除历史记录引用，保留正常业务 |
| 配置2 | 每次打开使用新键写入无界商品缓存 | 相同商品在 cache 中产生多个键且 GC 后仍可达 | 用商品键复用并限制缓存容量 |
| 干扰项 | 只看单个 JS heap 数值便确认泄漏 | 一次分配峰值，没有重复或回收后对照 | 隐藏数值或只减少打开次数 |

## 三级提示

1. 打开 More tools > Performance monitor，固定页面与每组 5 次开关，先记录空闲基线。
2. 在 Memory 使用 Collect garbage 后再次记录；不要把临时峰值直接称为泄漏。
3. 核对两条可能的保留或回归原因：关闭预览后历史数组持续保留 MemoryVisit；每次打开使用新键写入无界商品缓存。保持正常结果并复测。

## 边界、恢复与来源

正常结果保持 SKU、数量与业务校验值一致。相同 VM、批次和空闲条件比较；停止只清理本页资源。实际 GC、快照与 Recorder 证据须在工具核对，页面容器计数不等于堆快照。
