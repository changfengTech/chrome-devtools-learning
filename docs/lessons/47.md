# 47 · 排序、修复与复测

由 pnpm docs:lessons 生成。内容源 src/data/quality.json；生成与合同 scripts/generate-quality.mjs。本页含教师参考答案。

## 学习目标与原理

按影响、证据和成本排序并公平复测。按用户影响、因果证据和成本排序。固定条件做多轮前后对照，比较指标中位数及实际业务，而不只挑一次最高分。

### 优先级来自证据

主图等待需要 Network / LCP 关联；重复主线程工作需要 Performance 栈证据。改动预算不替代根因确认。

### 同条件多轮

每阶段导入三份独立 Navigation 报告，固定版本、设备、限速方法、类别和目标状态。比较 LCP 或 TBT 中位数，说明波动。

### 指标之外

小实验的改善不构成线上预算。检查结果一致、其余指标、人工键盘与遗留问题，避免把负担转移到别处。

## 交互演示

在修改预算内选任务并验证。在三点预算内选择改动；比较影响、依据与成本，而不是只数任务；读取多轮示意样本的中位数，识别条件变化。模型不计完成。

## 商城实战

主图返回很晚，或重复的商品处理阻塞主线程；只改按钮颜色后，体验并没有相应改善。

1. 准备故障并打开目标，固定 Desktop、四类别、限速方法；分别运行三次 Navigation 并导入 JSON。
2. 在 Network / Performance 关联主图等待或 normalizeCatalog 重复工作，记录实际证据。
3. 按影响、证据和成本排序，选择最小针对性方案；颜色调整不算性能修复。
4. 应用服务器对照，在相同设置下对新目标再运行三次；不要导入同一 fetchTime 的重复文件。
5. 比较 LCP 或 TBT 中位数、正常结果和其它检查项；本地受控负载要求趋势改善，不把数值当线上目标。
6. 完成实际人工路径检查，记录剩余限制和恢复条件，再提交章内 / 章末报告。

## 独立挑战与答案

提交改善依据和剩余限制。输入与故障随机变化，可能再次抽到同类。

| 配置 | 根因 | 证据 | 针对性验证 |
| --- | --- | --- | --- |
| 配置1 | 关键主图响应被延迟 | 三份 LCP 与主图等待证据一致 | 缩短实际关键图片等待，保持内容 |
| 配置2 | 商品归一化被重复执行 | 三份 TBT 与 normalizeCatalog 重复调用对应 | 复用商品处理结果，保留相同输出 |
| 干扰项 | 所有审计建议同样优先 | 只看一次最高分或调过限速后的结果 | 只改颜色并选择最好的一次结果 |

## 三级提示

1. 准备故障并打开目标，固定 Desktop、四类别、限速方法；分别运行三次 Navigation 并导入 JSON。
2. 按影响、证据和成本排序，选择最小针对性方案；颜色调整不算性能修复。
3. 比较两种可能原因：关键主图响应被延迟；商品归一化被重复执行。用本次实际证据选择最小对照。

## 边界、恢复与来源

固定版本、设备、限速、状态和类别；保留正常 SKU / 数量。真实报告、页面结果与工具操作分列，结束后恢复覆盖、视口和限速；不把课堂结论当作全面质量认证。
