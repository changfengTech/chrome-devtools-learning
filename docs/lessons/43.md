# 43 · Detached DOM 为什么仍在内存里

由 pnpm docs:lessons 生成。内容源 src/data/memory.json；生成与合同 scripts/generate-memory.mjs。本页含教师参考答案。

## 学习目标与原理

理解脱离文档却仍可达的节点。Detached 只说明节点不在文档中，不自动表示泄漏。要沿 Retainers 找业务结束后仍不必要的强引用，并在相同操作下验证。

### 文档连接与可达性不同

remove() 断开 DOM 父子关系，却不会删除 JS 数组或 Map 里的引用。父节点被保留时，其子树也可能被保留。

### 沿根追踪

在 Heap snapshot 用 Detached 或 DetachedProductDialog 筛选，检查 closedDialogs / selectedDetails，再追到 window.memoryLab。

### 避免调试器制造保留

Elements 的选中节点、$0、Console 输出或全局变量都可能保留节点。快照前清理调试器引用，再重复；不要用页面计数当作 GC 证明。

## 交互演示

移除 DOM 并切换外部引用。从文档移除节点；切换数组和 Map 的外部引用；释放最后一条根，观察可达标记而非立即 GC。模型不计完成。

## 商城实战

关闭的商品弹窗已从页面消失，却仍被数组或选中项索引持有，子树继续可达。

1. 预热后拍 A，重复 5 次开关并拍 B；不要先将目标节点存成全局变量。
2. 在快照筛选 Detached 与 DetachedProductDialog，区分文档内和脱离节点。
3. 选一个实例，在 Retainers 追到 closedDialogs 或 selectedDetails 以及 window.memoryLab。
4. 只 remove DOM 的对照不会清理外部引用；先预测结果再复测。
5. 选择释放相应外部引用的对照，重复相同批次，比较 C 的存活增量。
6. 记录根路径、正常弹窗是否可用和调试器自身保留的排除方法。

## 独立挑战与答案

追踪新残留节点并验证释放趋势。输入与故障随机变化，可能再次抽到同类。

| 配置 | 根因 | 证据 | 针对性验证 |
| --- | --- | --- | --- |
| 配置1 | closedDialogs 数组保留已关闭弹窗子树 | DetachedProductDialog.node 已断开文档且 closedDialogs 仍可达 | 清空关闭弹窗对应数组引用 |
| 配置2 | selectedDetails Map 仍指向已关闭节点 | 同一 detached 节点由 selectedDetails 的访问键保留 | 删除 Map 中已结束详情引用 |
| 干扰项 | 只要 Detached 就必然是漏洞 | 页面已不可见，所以对象一定不可达 | 只再次调用 node.remove() |

## 三级提示

1. 预热后拍 A，重复 5 次开关并拍 B；不要先将目标节点存成全局变量。
2. 选一个实例，在 Retainers 追到 closedDialogs 或 selectedDetails 以及 window.memoryLab。
3. 核对两条可能的保留或回归原因：closedDialogs 数组保留已关闭弹窗子树；selectedDetails Map 仍指向已关闭节点。保持正常结果并复测。

## 边界、恢复与来源

正常结果保持 SKU、数量与业务校验值一致。相同 VM、批次和空闲条件比较；停止只清理本页资源。实际 GC、快照与 Recorder 证据须在工具核对，页面容器计数不等于堆快照。
